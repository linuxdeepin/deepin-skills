# Eval: 搜索超时与中断失效排查

## 任务

用户反馈：输入关键词后搜索界面一直转圈，大约 25 秒后才显示「无结果」。daemon 日志中有 `Worker timeout - Name: ...`。插件实现是同步扫描一个大目录树并累积结果。请分析原因并给出修改方案。

## 期望输出

回答应：
1. 指出 25 秒是 daemon 对单次搜索的超时，超时按无结果处理，插件不会收到通知
2. 指出根因是 `Search` 不可中断且耗时过长，`Stop` 无法让它提前返回
3. 给出改造方案：用原子/加锁的标志按 `mID` 记录中断，搜索循环中周期性检查并提前返回
4. 建议缩小搜索范围、提前用规则过滤、限制结果数量、必要时改为增量/异步方式
5. 说明长时间阻塞会占住事件循环，导致 DBus 无法响应 `Stop`
6. 说明 daemon 在同一插件上一次搜索未结束时会跳过新搜索

## 验证要点

- [ ] 正确解读 `Worker timeout` 为 25 秒单次搜索超时
- [ ] 指出 `Search` 不可中断是根因
- [ ] 给出按 `mID` 记录中断并在循环中检查的方案
- [ ] 给出性能优化建议（预过滤、限制结果、缩小范围）
- [ ] 说明阻塞事件循环会阻碍 `Stop` 响应
- [ ] 说明同一插件上一次搜索未结束会跳过新搜索

## 评分标准

| 等级 | 条件 |
|------|------|
| ✅ **PASS** | 定位到可中断性缺失与性能问题，给出中断机制改造与优化建议 |
| ⚠️ **PARTIAL** | 指出超时问题但只建议优化性能，未实现中断机制 |
| ❌ **FAIL** | 建议调大 daemon 超时时间，或声称超时后插件会收到通知 |

## 反模式检查

- [ ] 未建议修改 daemon 的 25 秒超时来「解决」问题
- [ ] 未使用阻塞等待实现搜索
- [ ] 未声称 `Stop` 一定会在超时前被调用
