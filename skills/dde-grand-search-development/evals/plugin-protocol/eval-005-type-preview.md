# Eval: 结果项的 type 与预览插件配合

## 任务

用户的插件返回文本文件搜索结果。用户反馈「结果能显示，但点击后预览是空白的通用界面，希望能像内置文件搜索那样直接显示文件内容预览」。请分析原因并给出修改方案。

## 期望输出

回答应：
1. 说明 `type` 字段用于匹配预览插件，不是界面展示字段
2. 说明前端取 `item.type` 作为 MIME type，与预览插件 `.conf` 的 `Mimetypes` 匹配
3. 指出文本文件应将 `type` 填为 `text/plain`（真实 MIME type），才能命中内置文本预览插件
4. 说明自定义 `type` 值会落到通用预览
5. 说明 `type` 为空会导致该结果项被 daemon 直接丢弃
6. 说明预览插件的 `Mimetypes` 以 `:` 分隔，支持 `text/*` 形式的前缀通配

## 验证要点

- [ ] 指出 `type` 用于匹配预览插件而非展示
- [ ] 说明应填真实 MIME type（如 `text/plain`）以复用内置预览插件
- [ ] 说明自定义值会落到通用预览
- [ ] 说明 `type` 为空会导致结果项被丢弃
- [ ] 提到预览插件的 `Mimetypes` 匹配规则（分隔符或通配）
- [ ] 未建议插件自行实现预览界面作为首选方案

## 评分标准

| 等级 | 条件 |
|------|------|
| ✅ **PASS** | 准确定位 `type` 取值问题并给出填真实 MIME type 的方案 |
| ⚠️ **PARTIAL** | 指出 `type` 影响预览，但未说明应填真实 MIME type 或未提到空值被丢弃 |
| ❌ **FAIL** | 把 `type` 描述为展示字段，或建议改 `name`/`icon` 来解决预览问题 |

## 反模式检查

- [ ] 未把 `type` 描述为界面展示字段
- [ ] 未声称第三方搜索插件可以注册自己的预览插件（预览插件是独立的 `.so` 体系）
- [ ] 未建议把 `type` 留空交由框架猜测
