# Eval: 说明搜索结果的流转与解析限制

## 任务

用户想开发一个返回文件搜索结果的全局搜索插件，计划一次返回 300 个匹配文件，分 3 个分组，每组 100 个。请说明 daemon 会如何处理这些结果，以及插件需要遵守哪些解析限制。

## 期望输出

回答应：
1. 说明结果 JSON 的结构：`ver` / `mID` / `cont[].group` / `cont[].items[]`
2. 指出 **100 项是跨所有分组累计的上限**，300 项会被截断到 100 项，而不是每组 100 项
3. 指出 `item`/`name`/`type` 任一为空的结果项会被静默跳过
4. 指出 `group` 为空的分组会被整体跳过
5. 指出结果 JSON 的 `ver` 必须为 `"1.0"`，否则整个结果集被丢弃
6. 建议插件只返回最相关的少量结果

## 验证要点

- [ ] 指出 100 项上限是**跨分组累计**，纠正用户「每组 100」的理解
- [ ] 列出 `item`/`name`/`type` 三个必填字段，并说明为空时该结果项被跳过
- [ ] 说明空 `group` 会导致分组被跳过
- [ ] 说明结果 `ver` 必须为 `1.0`，不匹配时整个结果集被丢弃
- [ ] 给出了减少返回数量的建议
- [ ] 未声称插件可以设置 `itemLevel`/`itemTailer` 等扩展属性

## 评分标准

| 等级 | 条件 |
|------|------|
| ✅ **PASS** | 准确说明跨组累计 100 项上限、三个必填字段与 `ver` 校验，并给出合理建议 |
| ⚠️ **PARTIAL** | 说明了 100 项限制但误认为按组计算，或漏掉 `ver` 校验 |
| ❌ **FAIL** | 未指出任何解析限制，或声称第三方插件可设置扩展属性 |

## 反模式检查

- [ ] 未把 100 项上限描述为「每组 100 项」
- [ ] 未声称第三方插件可设置 `itemLevel`/`itemTailer`/`itemWeight`
- [ ] 未把 `type` 描述为界面展示字段
